# Zdroid backlog

Remaining Android feature gaps, device reports and unfixed review findings. Every item was rechecked against the code on 2026-11-12, and the ones marked "seen" were reproduced that day on the tablet with 0.17.0.

## Complete native Zed AI integration

The app initializes upstream `agent_ui` and `acp_tools`, including the agent panel and context-server UI; `agent`, `acp_thread`, and `context_server` are transitive dependencies.

Since 0.9.17 the app also runs Zed's model providers (`copilot_chat::init`, `language_model::init`, `language_models::init`, `web_search::init`, in the order of Zed's `main()`), so the native agent and the inline assistant work with your own API keys, including OpenAI-compatible endpoints (a LiteLLM gateway, for example). An Android-gated edit to `language_models::register_language_model_providers` leaves out the local model servers (Ollama, LM Studio, llama.cpp); a remote one can be added as an OpenAI-compatible provider. The gate has to be at registration: user-defined compatible providers can share those IDs, so unregistering afterwards would remove them too. Zed accounts stay out: the app skips `client::init` (sign-in actions), `RefreshLlmTokenListener`, `web_search_providers::init` and `copilot_ui::init`, and three Android-gated edits to Zed's crates hide the rest: `language_models::register_language_model_providers` skips the Zed-hosted provider (constructing it needs `RefreshLlmTokenListener`, which panics when it isn't registered), `ai_onboarding::AgentPanelOnboarding` shows only the API-key setup, and `AgentPanel::should_render_new_user_onboarding` ignores empty history. Zed doesn't call `language_models::init_extension_proxy` at v1.28.1, so extension-provided model providers stay off here too; enable them when Zed does.

Still unverified on a device: streamed responses and tool calls through an OpenAI-compatible endpoint, inline edits, API keys surviving a restart (Android Keystore), Copilot Chat's GitHub sign-in, and local MCP servers in the Ubuntu runtime (including the sandbox fallback), as opposed to servers on an SSH host. Copilot edit prediction is not initialized. Android's API-key card in a native agent thread has no dismiss button (Zed's card has one through `ZedAiOnboarding`), so it stays until a provider is configured.

**External agents under the Ubuntu runtime.** Claude Agent and Codex come from the ACP registry as npm packages, which Zed installs with its managed Node into `external_agents/registry/npx/` under its data directory (`LocalRegistryNpxAgent` in `agent_server_store.rs`). The managed Node is a Linux build that runs in the runtime, so npm picks the glibc `linux-arm64` builds of their CLIs, which read the runtime's `/etc/resolv.conf` and CA certificates. Codex's command sandbox doesn't start locally, as the release caveats say.

## Scrolling a full-window editor runs at 70–85 fps on the 120 Hz panel

Seen on 2026-11-12: a 3-second finger drag (`adb shell input swipe`) over `uv.lock`, with the editor filling the window, presented 70–85 frames a second, and 39–68% of the gaps between frames were longer than one refresh. With the terminal panel taking the bottom half, the same drag ran at 115 a second with one late frame in 125, so the cost grows with the text on screen.

A profile on 0.9.21 (2026-10-29) found `android_main` spending about 12.5 ms of CPU per frame on the prime core at its maximum clock, so the CPU scheduler can't help; a performance hint session changed nothing (`crates/gpui_android/docs/workarounds/choreographer-vsync.md`). Each frame's main-thread time split into painting glyphs (24%: `TextSystem::raster_bounds` 12.6% and `WgpuAtlas::get_or_insert_with` 8.6% of the thread's own time, two locked hash lookups per glyph per frame), the editor's layout (about 20%), sorting sprites and uploading them to the GPU (about 10%), and stack switching (7%), the only part desktop doesn't pay. 0.9.23 removed the stack switching (`crates/gpui_android/docs/workarounds/stacker-android-stack-limit.md`). The per-glyph lookups, unchanged at Zed v1.28.1, are the largest remaining cost, and reducing them means changing gpui's glyph caching.

## Open findings from the 2026-10-26 and 2026-10-27 reviews

The Android audit, the review of that week's PR stack and the two upstream-divergence audits found these.

- **Restoring the last session picks the main window by timestamp.** gpui_android doesn't implement `Platform::window_stack`, so the restore in `lib.rs` takes the window whose workspace was saved last. That column has one-second precision, so two windows saved in the same second come back in no fixed order, and the main Activity can restore the other window's workspaces. The app restores only that one window, with all of its workspaces, so in DeX a second window doesn't come back after a force-stop, and Zed 1.28's fix for two windows on the same SSH host, ported in 0.17.0, only matters once more than one window is restored. Fix: implement `window_stack()` with the main window first, or persist the main window's id. Tablet check: in DeX, open a second workspace window, edit in both, force-stop and relaunch; the main window must come back with its own workspace.

## Open after the 2026-11 merge review

- **Terminal touch scrolling moves by whole rows.** A finger drag on the terminal scrolls the grid a row per row of travel, because `Terminal::determine_scroll_lines` (`crates/terminal/src/terminal.rs`) turns pixels into whole lines. That reads as stepping next to the editor's pixel scrolling. A sub-row variant would keep a fractional offset in the terminal element and round it at paint. Deferred: correct as it is, and the editor's touch scrolling is where the time went.

## Open from the final pass, 2026-10-31

Seen on the tablet while testing 0.11.0, none of them caused by that release:

- **Alt reads "option" in shortcut hints (seen).** `PlatformStyle::platform()` in `crates/ui` treats every OS it doesn't know as Mac, and `keybinding.rs` names Alt from it, so the command palette shows `ctrl-option-j`. gpui's own `display_modifiers` already says "alt" on Android. Changing `PlatformStyle` needs a look at its other uses.

Not checked on the tablet:

- **Choose from Local Folders in the agent archive.** It only appears for an archived thread with no folder. None existed, and an empty window's agent panel has no message box to start one, so the keep-alive in `open_local_folder` has only been compiled.
- **Swiping the app away during first-launch extraction.** It needs a clean install, which deletes the home folder, so try it on the next one.
- **Dragging a scrollbar thumb with a finger, and pressing its track.** 0.14.0's merge conflicted in the code that claims these touch drags. Resizing a dock by dragging its edge with a finger works (seen). On 2026-11-12 the editor's minimap covered its scrollbar, and the touch drag there scrolled the text.

Considered and left as they are:

- **The status bar's buttons are hard to press.** In fullscreen with gesture navigation on One UI, Android's mandatory gesture area is the bottom 38 px and the status bar lies inside it, so presses there go to One UI's `TaskbarWindow` rather than Zdroid. A finger's press only works on the one pixel row above that area, and a mouse's or trackpad's on about the buttons' top 10 px (2026-11-01). Keeping the window out of `mandatorySystemGestures` avoids it at the cost of strips at the screen's top and bottom. A test build of 0.13.0 did that, and the owner preferred a window that fills the screen (2026-11-01).
- **A trackpad pinch does nothing.** gpui has `PinchEvent`, which the image viewer zooms with, and `translate_motion` could make one from `CLASSIFICATION_PINCH`'s two fake fingers. Nothing else in Zed uses it, and pinches never worked here.
- **A mouse's Back button does nothing.** On One UI it reached the window as a key event with no pointer event, and Zed's navigate-back needs the pointer's `BUTTON_BACK` (virtual mouse, 2026-11-01). It didn't work with pointer capture either.
- **A very fast two-finger flick can do nothing.** On a virtual trackpad, half the pad's height in 100 ms didn't scroll 2 times in 10, with the cursor hidden or visible. At 150 ms and slower it never missed, in 30 tries (2026-11-01). The cause wasn't looked into, and nothing like it has been reported on the real pad.
- **A second mouse button pressed while one is held does nothing.** Only `ACTION_DOWN` and `ACTION_UP` press and release a button in `events/mouse.rs`, which is all a chord would need `ACTION_BUTTON_PRESS` and `MotionEvent.getActionButton` for. Nothing in Zed uses chords.
- **A long press doesn't vibrate.** Android's views call `performHapticFeedback(LONG_PRESS)` when a long press does something, so a drag starting from one would too. gpui has no call for it, and the reference tablet reports no vibrator capabilities and has touch feedback off, so it couldn't be felt or checked there.
- **Paste in the terminal with an image on the clipboard sends Ctrl+V (since 0.12.0, from Zed's code).** Zed does this so that terminal agents can read the system clipboard themselves, which they can't on Android. In a shell, it makes the next key literal. Changing it would need an Android-only edit to `terminal_view.rs`.
- **Zed's path picker answers every path prompt.** It takes one path, doesn't filter by file or folder and doesn't show the caller's title, so the agent's Add Images attaches one image per pick and Clone Repository's picker doesn't say what it's for. A Download from a project on a Windows host also gets that host's path rules in a picker for this device's paths (read in the code, not seen). Fixing these means changing Zed's `OpenPathDelegate`. See `crates/gpui_android/docs/workarounds/path-prompts-use-zed-picker.md`.
- **Android's "pasted from" toast.** `readClipboardText` calls `getPrimaryClip`, which on Android 12 and later can show the system's clipboard-access toast when the clip came from another app, and Zed reads the clipboard to enable Paste in menus. Reading `getPrimaryClipDescription` instead for those checks would need gpui to tell the two reads apart. Tablet check: copy text in another app, come back to Zdroid and open a menu; a toast there is this.
- **R8 stays off** (`isMinifyEnabled`). `classes.dex` is 5.8 MB of a 108 MB APK, mostly AndroidX and Kotlin's standard library, so shrinking would save about 4 MB. Rust and GameActivity's native code reach classes by name over JNI, and a missed keep rule fails only at runtime, on whichever path it hits.
- **`ureq` in the updater.** `updater.rs` downloads with its own HTTP client instead of the app's. Moving it to `cx.http_client()` would drop a dependency, but a mistake there can't be fixed by an update, so it stays unless `ureq` becomes a problem.
- **Vulkan pre-rotation.** wgpu always asks for an identity `preTransform`, so in landscape the compositor rotates each frame from the panel's portrait frame. Android recommends rendering rotated instead, which needs changes in wgpu and gpui's renderer. Measure composition with `dumpsys SurfaceFlinger` on the tablet first.

## Findings from 0.10.0 on the tablet, 2026-10-29

Logcat of 0.10.0 (versionCode 65) on the tablet, from a fresh install through an SSH remote project, and the owner's use of it.

- **Google Antigravity doesn't start locally (can't be fixed here).** The registry's only Linux build, `agy_acp_server.par` for `linux-aarch64`, links Google's tcmalloc, which aborts with `CHECK in AllocSlow: FATAL ERROR: Out of memory trying to allocate internal tcmalloc data ... is something preventing mmap from succeeding (sandbox, VSS limitations)?`. The tablet's kernel is built with `CONFIG_ARM64_VA_BITS=39` (`/proc/config.gz`, 5.15.189-android13), and tcmalloc places its memory at addresses that need a 48-bit address space, so the kernel ignores its placement hints. The engine doesn't trap `mmap` (`bpf.rs` test `untrapped_syscalls_pass_anywhere`). It works on SSH remotes; locally it needs a Google build for 39-bit kernels.
- **A project's own tool versions don't reach its language servers.** The app loads root's login shell environment once at launch, in the home folder (`runtime_setup::load_login_environment`), and the project environment is that one (`project/src/environment.rs`'s Android gate). Desktop Zed loads another login shell in each project's folder, so a version a project pins in `mise.toml` or `.nvmrc` reaches its language servers there; here it applies only in the terminal. The gate could run the same `util::shell_env::capture` in the project's folder, but its PATH would have to reach that project's spawns as their own `ZD_GUEST_ENV`: `util::command::Command::envs` sets PATH through `zdroid_hooks::guest_env_for_path`, which starts from the process's `ZD_GUEST_ENV`, and the farm would have to mirror each project's folders.
- **`/system_ext/bin` leaks into the guest PATH.** `zdroid_hooks::merge_guest_path` drops Android's own folders from a spawn's PATH before putting it ahead of the guest PATH, but its list has `/system/` and not `/system_ext/`, which Android's PATH also holds. So a language server's `ZD_GUEST_ENV` PATH starts with `/system_ext/bin` (seen in 0.18.0's tablet check, 2026-11-12). Harmless while the rootfs has no such folder; add it to `HOST_ONLY_PREFIXES`.
- **The settings file opens as JSON, not JSONC.** Zed's default `file_types` treat `**/{zed,Zed}/{settings,keymap,tasks,debug}.json` as JSONC, and the app keeps them in `<files>/config/`, so `settings.json` opens as JSON and the JSON server flags every comment ("Comments are not permitted in JSON.", 0.18.0 on the tablet, 2026-11-12). A `file_types` default for `**/config/{settings,keymap,tasks,debug}.json` in the app's defaults would match Zed.

## Engine review of 2026-10-29 (`zd_engine_core`, `zd_loader`)

A read of Dylan's engine as merged in 0.10.0. Fixes in Dylan's crates go to him as well (FORK.md, "Syncing Dylan's repo").

- **Blocking calls the handler makes for the guest can't be interrupted (seen).** Since `c28dd018d5` the SIGSYS handler blocks every other signal while it runs (`zd_loader/src/handler.rs:119`). `connect`, `accept4`, `sendto` (glibc's `send`), `sendmsg`/`recvmsg`, `openat` on a FIFO and the `linkat` copy fallback therefore ignore signals while they block: `timeout 2 cat` on a FIFO with no writer ignored the SIGTERM and needed `timeout`'s SIGKILL, Ctrl+C on `python3 -m http.server` waits for a request, and `alarm()` timeouts don't fire. The mask exists so a Go signal handler never sees the loader's registers; fixing this needs a design from Dylan.
- **`..` across a binding edge resolves on the host (seen).** `translate.rs` picks the binding on the clamped, not normalized, path (`translate.rs:90` and `:99`), so `ls /tmp/../etc` lists the runtime's marker folder instead of the guest's `/etc`, and `/usr/../tmp` reaches the rootfs's own `/tmp`. Relative paths go to the kernel unclamped (`translate.rs:70-72`): from `/`, `ls ..` lists the app's files folder (`rootfs`, `zd-runtime`, `external_agents` and the rest). `rewrite_symlink_target` already does the needed `tree_of`/`escapes` check for symlinks.
- **Exec limits below Linux's (seen).** The rebuilt argument vector must fit 256 KiB (`VECTOR_GAP`, `main.rs:40`) against the kernel's ~2 MiB, and `execve` never returns E2BIG: 60,000 short arguments (about 350 KB) fail with `zdload: argument vector too large` and exit 126, so `rm *` over ~30k files does too. A guest `PATH` of 4096 bytes or more makes every exec fail with `zdload: an engine variable exceeds 4096 bytes` (`config.rs:52`); the PATH is only needed for symlink-farm lookups.
- **Smaller ones (reviewers, rechecked in the code).** Exec failures after the preflight end the process with exit 127 for a missing file and 126 otherwise, where `execve` would return ENOENT or ENOEXEC (`main.rs:376-420`); guest pointers other than null fault in the handler instead of returning EFAULT (`cstr_bounded`); `setuid(-1)`/`setfsuid(-1)` under fake root store `u32::MAX` (`identity.rs`); `sigaction(SIGSYS, &sa, &sa)` writes the old action before it reads the new one, so the guest's new SIGSYS action is dropped (`handler.rs:1520-1538`); `PT_GNU_STACK` is ignored (`load.rs`); ET_EXEC segments are mapped `MAP_FIXED` without a check against the loader window (`load.rs`, `map_segment`); `#!/bin/bash\r` scripts run where Linux refuses them (seen; `shebang.rs`); the scratch pool can overflow a small alternate signal stack with 64 threads blocked in trapped calls (`scratch.rs:69`).
- **Soundness (reviewers).** `config::get_mut()` and `identity_mut()` hand out `&mut` to globals that other threads read (`config.rs:435`, `handler.rs:794`), which is undefined behavior in Rust; `identity_mut` is used while the guest runs, against `get_mut`'s own safety comment. The practical effect is torn reads such as `getgroups` racing `setgroups`.
- **Build and CI.** CI tests `zd_engine_core` only with its `std` feature and never lints or tests `zd_loader`; the build container has no clippy. Clippy on the host found one deny-level error (`not_unsafe_ptr_arg_deref` on `zd_main`) and four warnings, and rustc warns that `outline-atomics` is an unstable target feature. The loader ships 477 KiB of DWARF in its 620 KiB (`debug = "limited"`, `strip = false`); split it into the symbols artifact. The image base is written in `.cargo/config.toml`, `zd_engine_core.rs` and `verify.sh`, and `verify.sh` checks only against its own copy.

## Input review of 2026-10-26: open findings

An audit of `crates/gpui_android`'s input code found 22 problems; these are still open. The first found, captured trackpad and mouse events dropping the modifier keys, sat unrecorded until it showed up as "Ctrl+click on a link does nothing"; that is why the rest are listed here.

**Mouse and trackpad**

4. **Gpui is never told when the pointer leaves a window.** Android sends `HOVER_EXIT` before every press too, so it doesn't mean that. The hover-status callback is stored but never called, and `is_hovered` returns false, so hover highlights can stay after the pointer leaves.
5. **S Pen buttons aren't mapped.** `button_from_state` ignores the stylus button bits, so the pen's side button doesn't right-click.

**Touch**

- **A long press outside the editor and the terminal ends as a tap when the finger lifts.** Only those two claim gpui's `LongPressEvent`.

**Keyboard and IME**

11. **The IME doesn't know where the caret is.** `update_ime_position` is empty and `ZdroidInputConnection` doesn't implement `requestCursorUpdates`, so floating keyboards and handwriting input can't position themselves.
12. **InputConnection contract gaps:** `setComposingRegion` and `performContextMenuAction` aren't implemented, and `newCursorPosition` is ignored. `setSelection` records the IME's selection for its next edit, without moving the editor's.
13. **The keyboard hides by polling** `input_handler.is_some()`, with a `text_for_range(0..1)` probe and a selection poll, instead of when focus leaves the text field. (Text fields show it through `request_virtual_keyboard`; see `crates/gpui_android/docs/ahead-of-upstream.md`.)

## Upstream follow-ups

Left from the 2026-08-07 merge, which brought upstream's mobile APIs, and upstream bugs seen on the tablet. Recheck these at each Zed sync.

- **Back handler and text input configuration.** gpui_android doesn't implement `set_back_handler` or `set_text_input_configuration`. Nothing in Zed v1.28.1 calls the first, and gpui forwards the second but no Zed crate supplies a configuration. `crates/gpui_android/docs/ahead-of-upstream.md` says what to grep for at each sync.
- **Embedded run loop and dispatcher.** `Application::run_embedded` still invokes `Platform::run`, and `ThreadedDispatcher` is gated to tests and benchmarks at v1.28.1, so neither replaces the Android event loop or dispatcher. Recheck if upstream adds a production mobile dispatcher.
- **`spawn_when_idle`.** `AndroidDispatcher` doesn't implement `dispatch_on_main_thread_when_idle` or `idle_time_remaining`, so `ForegroundExecutor::spawn_when_idle` falls back to a low-priority main-thread task and ignores its timeout. Nothing in Zed v1.28.1 calls it.
- **Audit git CLI spawn sites.** git2 is gone; `crates/git/src/repository.rs` and `project/src/git_store.rs` spawn `git` per operation through the farm and the engine loader (verified working on-device for status/trust). Sweep for spawn sites that assume desktop git semantics (pager, hooks, credential helpers) under the runtime's git.
- **The `sandbox` crate on Android.** The app pulls it in through `agent`, `acp_thread` and `agent_ui`, and on Android its `wrap()` returns `SandboxError::UnsupportedPlatform`. Check which agent tool calls reach it and what the user sees then.
- **Idle remote connections stop sending heartbeats.** In `crates/remote/src/remote_client.rs::heartbeat`, a successful ping takes the `continue` branch, which skips re-arming `keepalive_timer`, so the next ping waits until the server sends something. On the tablet (0.17.1, 2026-11-12) an idle SSH project sent nothing for minutes, and a stalled session went unnoticed until a file was opened; after that, five missed pings started the reconnect as intended. The code matches v1.28.1. Check: leave a remote project idle, `kill -STOP` its `sshd-session` on the host, and look for "No heartbeat from server" in logcat within 10 s.
- **Closing a remote project leaves its connection open.** After Close Project on an SSH project, and after Remove Server on a server connected from the Open Remote dialog, the ssh master and the server's proxy kept running (0.17.1, 2026-11-12), so something still holds the project. `multi_workspace.rs` matches v1.28.1; not traced further. The master is Zdroid's child and ends with the app. Check: close the remote project, then `adb shell "ps -A | grep 'ssh -N'"` should list nothing.
